# 재고 조회 도구 정의서

- 작성일: 2026-10-12
- 대상: 실습 1 — 도구 정의서와 실패 사례 리디자인
- 상태: 문서 설계·검토. 실제 모델 실행 검증 전.

## 1. 이름

`get_inventory` — 특정 상품의 창고별 가용 재고 조회.

## 2. 하는 일 한 문장

승인된 창고에서 특정 SKU의 가용 수량을 읽기 전용으로 조회한다.

SKU(Stock Keeping Unit)는 상품을 구별하는 식별 코드다. `A-17`은 교재 예시이며 유일한 허용 SKU가 아니다. 가용 수량은 조회 결과에서 이용 가능한 재고로 제공하는 값이며, 총재고·예약 가능량과의 추가 관계는 이 실습에서 정의하지 않는다.

## 3. 언제 쓰고 안 쓰는지

### 사용 조건

- 사용자가 특정 상품의 재고 수량을 질문한다.
- 상품 SKU와 승인된 창고 코드가 모두 확정되어 있다.
- 인자가 아래 입력 규격에 맞는다.
- 예: “BUSAN-02 창고의 SKU A-17 재고를 알려 줘.”

### 사용하지 않는 조건

- 수량 변경·입고·출고·예약·구매 요청: 이 도구의 범위 밖이다. 조회 성공을 변경 성공으로 설명하지 않는다.
- SKU 누락·모호함: 비슷한 상품을 고르지 않고 정확한 상품 식별자를 질문한다.
- 창고 미지정·모호함·허용값 밖: 임의로 창고를 선택하지 않고 SEOUL-01 또는 BUSAN-02 중 의도한 창고를 질문한다.
- “부산 3번 창고”처럼 허용 코드로 확정할 수 없는 표현을 BUSAN-02로 바꾸지 않는다.
- 권한 확인 실패: 도구를 실행하지 않고 중단한다. 요청 문장만으로 권한이 있다고 판단하지 않는다.

질문으로 인자가 확정된 뒤에는 새로운 유효 요청으로 조회할 수 있다. 이것은 같은 잘못된 인자로 재호출하는 것과 다르다.

## 4. 인자 스키마

스키마(schema)는 도구 입력의 형식과 허용 조건을 정한 규격이다. 아래는 문서상 계약이며 실제 서버에 등록한 스키마가 아니다.

```json
{
  "type": "object",
  "properties": {
    "sku": {
      "type": "string",
      "minLength": 3,
      "maxLength": 32,
      "description": "사용자가 확인한 정확한 상품 SKU. 비슷한 상품의 코드를 추측하지 않는다."
    },
    "warehouse_id": {
      "type": "string",
      "enum": ["SEOUL-01", "BUSAN-02"],
      "description": "사용자가 지정하거나 확인한 승인 창고 코드."
    }
  },
  "required": ["sku", "warehouse_id"],
  "additionalProperties": false
}
```

- SKU의 길이와 창고 허용값은 교재 표 기준이다.
- `additionalProperties: false`는 이번 정의서의 보완이다. 지정한 두 인자 외에 원가 조회·수량 변경용 인자를 넣지 않는다.
- SKU 문자열의 형식 적합성과 실제 상품 존재 여부는 별개다. 길이가 맞는다고 존재하는 상품이라고 단정하지 않는다.
- 이 실습에서는 SKU 문자 종류·대소문자 변환·창고 별칭 규칙을 추가로 만들지 않는다.

호출 요청 예시(실행 결과가 아님):

```json
{"name": "get_inventory", "arguments": {"sku": "A-17", "warehouse_id": "BUSAN-02"}}
```

## 5. 반환 형식과 답변 근거

성공 결과 필드는 다음과 같다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `sku` | 문자열 | 조회한 상품 코드 |
| `warehouse_id` | 문자열 | 조회한 창고 코드 |
| `available_quantity` | 0 이상의 정수 | 가용 수량 |
| `checked_at` | 시간대가 포함된 날짜·시각 문자열 | 조회 결과의 확인 시각 |

필드 이름은 교재 §5 코드와 맞춘다. 수량의 비음수 정수 조건과 시간대 포함 조건은 문서상 보완이며 실행 검증 전이다.

### 최종 답변 규칙

- 수량 판단의 근거는 `available_quantity`, 시점의 근거는 `checked_at`만 사용한다.
- SKU·창고는 요청과 결과가 일치하는지 대조하기 위한 식별 정보다. 이를 이용해 가격·원가·판매 가능 여부 등 다른 결론을 추정하지 않는다.
- 내부 원가나 정의하지 않은 추가 필드가 섞여도 최종 답변에 인용하지 않는다.
- 오류를 재고 0으로 해석하지 않는다. 수량이 실제로 0인 성공 결과와 조회 실패를 구분한다.
- 필수 필드가 없거나 결과의 SKU·창고가 요청과 다르면 수량 답변을 중단하고 결과 확인이 필요하다고 알린다.
- 확인 시각을 실제 현재 시각으로 바꿔 쓰지 않는다. 오래된 결과를 최신 재고로 단정하지 않는다.
- 교재의 고정 수량 7과 고정 시각은 모의 예제다. 실제 재고·현재 조회 결과로 소개하지 않는다.

실행 계층에서도 필요한 반환 필드만 모델에 전달해야 한다. 문장으로 원가 인용을 금지하는 것만으로 유출 방지가 보장되지는 않는다.

## 6. 실패 정의와 뒤 행동

| 조건 | 다음 행동 | 자동 재시도 |
|---|---|---|
| SKU 미지정·형식 부적합 | 정확한 SKU를 질문하고 호출하지 않는다 | 없음 |
| `INVALID_SKU` | 상품 식별자를 다시 확인한다. 유사 상품으로 대체하지 않는다 | 없음 |
| 창고 미지정·모호함 | 허용 코드 중 의도한 창고를 질문하고 호출하지 않는다 | 없음 |
| `WAREHOUSE_NOT_ALLOWED` | 허용 창고를 질문한다. 같은 잘못된 인자로 재호출하지 않는다 | 없음 |
| 시간 초과·일시적 연결 실패 | 읽기 전용 조회를 동일한 유효 인자로 한 번 재시도한다. 또 실패하면 중단하고 조회 실패를 알린다 | 최대 1회 |
| 권한·인증 실패 | 중단한다. 권한 우회나 다른 창고로의 자동 변경을 하지 않는다 | 없음 |
| 결과 형식 불일치·요청과 다른 식별자·원인 불명 오류 | 중단하고 오류 또는 확인 필요 상태를 알린다. 수량을 추측하지 않는다 | 없음 |

- 통신 오류 재시도 정책: 사용자 선택으로 확정. 총 시도는 최초 호출과 추가 재시도까지이며 반복 루프를 만들지 않는다.
- `WAREHOUSE_NOT_ALLOWED`는 교재 §5 코드의 실제 반환 경로다.
- `INVALID_SKU`는 교재 §5 description에 있으나 예제 함수에 해당 오류를 반환하는 구현은 없다.
- 통신·권한·결과 오류 대응은 이번 실습에서 보완한 설계다. 실제 오류 코드 이름과 서버 구현은 아직 정하지 않았다.

## 문서 점검과 실행 상태

- 정의서 여섯 항목과 교재 실패 사례 세 가지를 대응시켰다.
- 관련 분석: [실패 사례 분석](🧪실패사례_분석.md)
- 모델 실행, MCP 서버 등록, 실제 재고 조회, 규칙 준수 실험은 하지 않았다.
- 교재 §5 예제는 SKU 길이·존재 검사와 반환 필드 제한을 구현하지 않는다. 실습 2에 들어갈 때 차이를 확인하며 지금은 코드를 변경하지 않는다.
