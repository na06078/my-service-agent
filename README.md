# 하루마켓 반품·교환 안내 챗봇 — 설계

아이펠 노드 "LLM 도구 사용과 MCP" 과제 제출 저장소입니다. 실습 1·2에서 만든 도구 정의서와 실행 기록, 실습 코드 전체, 그리고 이를 바탕으로 쓴 서비스 설계 문서를 함께 담았습니다.

## 서비스 소개

가상의 온라인 쇼핑몰 "하루마켓"에서 구매한 고객에게 반품·교환 정책을 안내하고, 본인 확인을 거친 주문의 반품·교환 가능 여부를 확인하며, 고객이 확인 버튼으로 승인한 접수를 만드는 챗봇입니다. 환불 금액 확정, 정책 예외 승인, 하자·배송 사고 판정은 챗봇이 결정하지 않고 상담원에게 넘깁니다.

챗봇 자체는 구현하지 않았습니다. 도구 계약·권한·관찰·중단 기준을 `design-packet.md`에 설계했습니다.

## 저장소 구조

```text
├── README.md               # 이 문서
├── design-packet.md        # 설계 패킷 일곱 항목
├── my-agent/               # 과제 지정 구조: 실습 1·2 산출물
│   ├── tool-definition.md  # 실습 1 도구 정의서 (get_inventory)
│   ├── 🧪실패사례_분석.md   # 실습 1 실패 사례 분석
│   └── traces/             # 실습 2 실행 기록 원문 trace-01 ~ trace-10
├── 01_도구정의/             # 실습 1 작업 원본
├── 02_도구실행/             # 실습 2-1~3: inventory_tool.py, 테스트, 실행기록(TXT+JSON)
├── 03_검색연결/             # 실습 2-4: Qdrant MCP 설정·검증 스크립트·실행 기록
└── 📋진행현황.md            # 실습 진행·검증 기록
```

`my-agent/`의 파일은 작업 폴더(`01_`~`03_`)의 원본을 과제 구조에 맞게 옮긴 것입니다. 원본과 내용이 같고, trace 파일 맨 위에 원본 경로를 적었습니다.

## 설계 결정 요약

**도구를 네 개로 나눈 이유**
정책(일반 규칙), 주문 사실(개인정보), 상태 변경, 사람에게 넘김의 네 책임으로 나눴습니다. 반품 가능 여부를 판정하는 도구를 따로 두지 않은 것은 주문 조회와 정책 검색의 결과를 조합하면 되고, 판정 도구를 추가하면 정책 검색과 책임이 겹쳐 모델이 잘못 고를 여지가 커지기 때문입니다.

**권한을 나눈 기준**
외부 상태를 바꾸는지로 읽기와 쓰기를 나눴습니다. 쓰기 승인의 근거는 모델이 채우는 인자가 아니라 하네스가 기록한 고객 행동(확인 버튼, 본인 확인)입니다. 실습 2에서 같은 질문에도 도구 설명 문장에 따라 모델 행동이 달라졌기 때문에(trace-06과 trace-07), 문장 규칙만 믿지 않고 서버가 최종 거절하게 했습니다.

**실패 뒤 행동을 정한 근거**
재시도는 일시적일 수 있는 오류에만 1회 허용하고, 같은 오류가 2회 나면 멈춥니다. 쓰기 도구는 중복 접수 위험이 있어 자동 재시도를 금지했습니다. 근거가 없거나 조항이 충돌하면 추측하지 않고 보류하거나 넘깁니다.

**실습에서 가져온 규칙**

- 모호한 식별자를 비슷한 허용값으로 바꾸지 않는다 — trace-03·06.
- 모델이 도구를 호출하지 않는 것도 정상 응답으로 처리한다 — trace-04·07의 `IndexError`.
- 결과를 다시 넣을 때 원래 질문을 함께 보낸다 — trace-01의 HTTP 500.
- 정책 원문에 없는 내용은 "자료에 없다"고 말한다 — trace-10의 근거 밖 단정.

## 실습 환경 (교재와 다른 점)

| 항목 | 교재 | 이 저장소 |

| LLM 서버 | Ollama `qwen3.5:2b` | llama.cpp `llama-server` b11429, Qwen 3.8 27B (로컬) |

모델이 다르므로 교재와 같은 출력은 보장되지 않습니다. 자세한 차이는 `02_도구실행/📘실습진행안내.md`, `03_검색연결/📘검색연결안내.md`에 있습니다.

## 실행하지 않은 것과 이유

- **챗봇 구현과 도구 서버**: 과제 범위가 설계 문서입니다. 정책과 주문은 `design-packet.md` 0번의 가상 데이터입니다.
- **하네스의 확인 버튼·서버 측 검증**: 설계만 했습니다.
- **설계 패킷 ⑥ 테스트 문항 실행**: 기대 동작만 적었습니다. ⑦은 실행할 때 채울 양식입니다.
- **사전 확인 실험(도구 정의 JSON 출력·채팅 템플릿 재현·토큰 수 비교)**: 이번 실습에서는 건너뛰었습니다. `colab-mcp` 실습이며 이 저장소의 결과물에는 포함되지 않습니다.
- **실습 1 정의서의 강화 규칙 구현**: SKU 길이·존재 검사, 반환 필드 제한, 통신 오류 1회 재시도는 문서 계약이며 `inventory_tool.py`에는 구현하지 않았습니다. 교재 함수와 같게 두고 차이를 관찰했습니다.
- **Claude Code·OpenCode 비교**: 로컬 llama-server의 내장 MCP 하나로 진행했습니다.

## 저장소에 포함하지 않은 것

`.gitignore`로 제외했습니다.

- `02_도구실행/.venv/` — 프로젝트 전용 Python 3.11 가상환경, 약 257MB
- `03_검색연결/임베딩모델/` — FastEmbed ONNX 임베딩 모델 `Qdrant/bge-small-en-v1.5-onnx-Q`, 약 65MB
- `__pycache__/`
- LLM 모델 파일은 처음부터 이 폴더 밖에 있어 포함되지 않습니다.

## 다시 실행하려면

Windows PowerShell 기준입니다. 설정 파일(`검색연결설정.json`, `라마서버_실습실행.ps1`)에는 작성자 PC의 절대 경로가 들어 있으므로 다른 PC에서는 경로를 고쳐야 합니다.

```powershell
# 1) 가상환경과 패키지
cd 02_도구실행
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r 의존성.txt

# 2) 모델 호출 없는 코드 검사
.\.venv\Scripts\python.exe .\테스트_재고도구.py

# 3) 재고 도구 (OpenAI 호환 LLM 서버가 http://127.0.0.1:8080 에서 실행 중이어야 함)
.\.venv\Scripts\python.exe .\inventory_tool.py
.\.venv\Scripts\python.exe .\inventory_tool.py --prompt "부산 3번 창고의 A-17 재고를 알려 줘" --description definition

# 4) 임베딩 모델 받기와 Qdrant MCP 검사
cd ..\03_검색연결
..\02_도구실행\.venv\Scripts\python.exe .\준비_임베딩.py
..\02_도구실행\.venv\Scripts\python.exe .\검증_MCP_저장검색.py
```
